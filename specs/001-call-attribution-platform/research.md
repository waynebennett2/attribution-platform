# Phase 0 Research: Call Attribution Platform

**Feature**: 001-call-attribution-platform | **Date**: 2026-08-10

Every item below resolves a technical unknown left open by the constitution (which fixes language, database and layering, but explicitly defers data-access technology to this plan) or by the spec's functional requirements. No NEEDS CLARIFICATION markers remain in the Technical Context.

## 1. Data access: Dapper vs EF Core

> **Superseded 2026-09-08** — Dapper and the .NET Infrastructure layer this section chose between are retired by the Apiche migration (§17–§18). Retained below as the historical record of *why* the original hand-written-SQL approach was chosen, since §18's stored-procedure design inherits the same underlying reasoning (hand-written, reviewable SQL over ORM-generated queries) even though the runtime technology changed.

- **Decision**: Dapper as the sole data-access technology, used only from the Infrastructure layer.
- **Rationale**: Two operations are correctness-critical and latency-sensitive in a way that benefits from hand-written, reviewable SQL rather than ORM-generated queries: atomic number allocation (FR-003, SC-004's 300ms bar) and idempotent CDR/Call Leg upserts (FR-017, FR-045). Both need explicit `INSERT ... ON DUPLICATE KEY UPDATE` / `SELECT ... FOR UPDATE SKIP LOCKED` control that EF Core would fight rather than help with. Using one data-access technology for the whole application (rather than mixing Dapper for hot paths and EF Core for CRUD) keeps Infrastructure simple and avoids two change-tracking mental models in one codebase, consistent with the "monolith-first" architecture style in the constitution.
- **Alternatives considered**: EF Core alone — idiomatic for the CRUD-heavy admin surface (pools, numbers, rules, users) but its change-tracker and generated SQL make the atomic-allocation and idempotent-upsert paths harder to reason about and test at the SQL level. EF Core + Dapper hybrid — gets the best of both but adds a second ORM/migration story for no benefit at this schema's size (~16 entities); rejected as unnecessary complexity for a monolith-first build.

## 2. Atomic number allocation on MySQL

- **Decision**: `SELECT id FROM tracking_numbers WHERE pool_id = @pool AND status = 'active' AND id NOT IN (<currently-held>) ORDER BY last_released_at LIMIT 1 FOR UPDATE SKIP LOCKED`, followed by an `UPDATE` inserting the allocation row in the same transaction.
- **Rationale**: `FOR UPDATE SKIP LOCKED` (MySQL 8.0.1+) lets concurrent allocation requests each grab a different available number without blocking on each other or double-allocating, satisfying FR-003's "no two concurrent sessions can ever hold the same number" guarantee under the SC-004 peak of ~57 requests/minute. This is why Storage is pinned to MySQL 8.0+ rather than an unversioned "MySQL" in Technical Context.
- **Alternatives considered**: Application-level distributed lock (e.g., Redis) — adds an operational dependency and a second source of truth for a load level (≤57 req/min) the database handles natively; rejected as premature. Optimistic concurrency (retry on conflict) — workable but adds latency variance under contention that a direct locked read avoids; rejected in favor of the simpler pessimistic approach given the write is already short-lived.

## 3. Idempotent ingestion and outbox-based publication

- **Decision**: CDR/Call Leg ingestion upserts on 8x8's own record identifier (natural key) with `INSERT ... ON DUPLICATE KEY UPDATE`, guarded by the ingestion checkpoint (FR-016). Publication to Google Ads/GA4 goes through an outbox table written in the same transaction as the qualification decision; a worker drains the outbox and records the idempotency key (FR-027) before calling out, so a crash between "sent" and "recorded" cannot double-publish on retry.
- **Rationale**: Directly implements Principle IV (idempotent, auditable operations) and FR-017/FR-027/FR-045 without introducing a message broker — at this scale (~57 allocation-path requests/minute, hourly CDR batches) a database-backed outbox is sufficient and keeps the deployment footprint to "API + workers + MySQL," matching the constitution's monolith-first guidance.
- **Alternatives considered**: A message queue (RabbitMQ/SQS) between qualification and publication — gives stronger decoupling but is unjustified infrastructure for this volume and reintroduces an idempotency problem (consumer-side dedup) the outbox table already solves at the database layer; deferred as a future extraction point if scale grows, per the constitution's "structured to allow future extraction" guidance.

## 4. Background worker architecture

> **Superseded 2026-09-08** — the dedicated `Attribution.Workers` host is retired by §19, which moves the same four responsibilities into Apiche's own scheduled-job configuration. Retained below because the isolation rationale (never let a slow 8x8 poll delay a DNI allocation request) still applies and still governs how §19's jobs must be scheduled relative to Apiche's HTTP-serving path.

- **Decision**: A separate `Attribution.Workers` host running four `IHostedService` loops — Ingestion (8x8 polling, FR-016), Publication (outbox drain, FR-025–FR-028), Alerting (FR-047 threshold evaluation), Retention (FR-040 purge/de-identify, FR-039 erasure) — deployed and scaled independently from the request/response API.
- **Rationale**: FR-043 requires no single point of failure in the visitor-facing allocation path; running ingestion/publication in-process with the API would couple their failure modes and resource contention (a slow 8x8 poll must never delay a DNI allocation request). A dedicated worker host can scale to zero or many instances independently and is simple to reason about — one loop, one responsibility, one crash-restart boundary.
- **Alternatives considered**: In-process `IHostedService` inside the API — simplest to deploy but violates the isolation FR-043 asks for. A full job-scheduling platform (Hangfire, Quartz.NET clustered) — adds a UI and storage model beyond what four fixed, always-on loops need; a plain hosted-service loop with the outbox/checkpoint tables already providing durability is sufficient.

## 5. Local username/password authentication with TOTP MFA (supersedes the 2026-08-09 federated-SSO decision, revised 2026-08-17)

> **Superseded 2026-09-08 by §20** — Basic Auth with a per-user long-lived credential replaces the JWT access/refresh pair and TOTP MFA described below; FR-046 and SC-016 need a corresponding spec amendment (see §20). Retained below as the historical record of the federation-to-local-auth decision, which is unaffected in substance (local accounts, not a federated IdP, remain correct) — only the token/session/MFA mechanics change.

- **Decision**: Every interactive user signs in with a local username and password plus a mandatory TOTP code (FR-046) — the same local-credential mechanism originally scoped only to the 2-account break-glass recovery path is now the platform's sole interactive sign-in method, provisioned for as many accounts as there are users. Sign-in issues a short-lived (5-minute) JWT access token and a longer-lived, rotating opaque refresh token (a random value, stored server-side only as a hash, per FR-046); the client exchanges the refresh token for a new access/refresh pair before each access-token expiry, and that exchange is refused once the account has been deactivated.
- **Rationale (token lifetime and refresh)**: SC-016 requires a deactivated user to lose access without waiting for a longer-lived session to expire. A 5-minute JWT bounds that staleness window tightly while keeping every API request's auth check a cheap, stateless signature verification, consistent with the stateless, horizontally-scalable API design (FR-043); the refresh token moves the one recurring database check (is this account still active?) off the hot path and onto the much less frequent refresh call, rather than requiring either a per-request database lookup or forcing re-entry of the password and TOTP code every 5 minutes.
- **Rationale (dropping federation)**: The 2026-08-09 decision to federate against the customer's identity provider was never exercised in this codebase — no HTTP endpoint for federated sign-in was ever built, since that path is inherently the identity provider's own redirect flow, and no live provider was available to build and test one against. The 2026-08-17 clarification formalises what was already true in practice: the only interactive sign-in this platform itself is responsible for is the local one. Revisiting federation remains possible later (the JWT-everywhere design of Principle VI does not preclude a provider-issued identity being exchanged for the same platform token shape), but is out of scope for this version.
- **Alternatives considered**: Keeping federation as a parallel, rarely-exercised path alongside local sign-in — rejected as needless surface area (an unused OIDC client library, a `Federated` identity type with no code path that ever creates one, a `GroupRoleMapper` nothing ever calls) for a capability the deployment does not use. A single long-lived session token instead of an access/refresh pair — rejected, since it would either force re-authentication with a TOTP code every 5 minutes (bad UX for an everyday admin login) or abandon the 5-minute staleness bound entirely (a real regression from what FR-046 already committed to).

## 6. Google Ads offline conversions integration

- **Decision**: Google Ads API's `ConversionUploadService` (click conversions, keyed on GCLID/GBRAID/WBRAID) for initial upload, and its adjustment/retraction endpoint for the corrections FR-044 requires.
- **Rationale**: This is the only Google Ads surface that accepts an offline (non-web-hit) conversion tied to a stored click identifier, and it is the one Google surface documented to support later retraction/adjustment — the capability FR-044 depends on existing at all.
- **Alternatives considered**: None materially different — Google Ads offers no second API for this use case; the only real decision is how failures are retried, covered by the outbox/idempotency design in §3.

## 7. GA4 Measurement Protocol integration

- **Decision**: Server-side Measurement Protocol POST, keyed on the GA4 client identifier captured at session time (FR-015, FR-026).
- **Rationale**: The Measurement Protocol is Google's only server-to-server path for GA4 events and is explicitly named in the spec's input description; it has no retraction endpoint, which is why FR-044 records GA4 corrections as "unpropagatable" rather than attempting one.
- **Alternatives considered**: None — this is the single documented integration surface for the requirement as stated.

## 8. Analytics for 8x8 Work ingestion

- **Decision**: Scheduled polling (default hourly, FR-016) against the Analytics for 8x8 Work API for Call Detail Records and Call Legs, authenticated per 8x8's own credential model, with an ingestion checkpoint (last successfully consumed position) persisted per feed so a restart resumes without gap or duplication.
- **Rationale**: The spec's own description mandates polling (no 8x8-side webhook/push capability is asserted), and FR-016 explicitly requires cadence changes to leave attribution outcomes unaffected — only achievable if matching always replays stored allocation windows rather than depending on ingestion timing, which the checkpoint-plus-idempotent-upsert design in §3 already guarantees.
- **Alternatives considered**: Real-time/streaming ingestion — not offered by the stated source (Analytics for 8x8 Work is polled), and Real-time dashboards are explicitly Out of Scope; rejected as solving a problem the spec doesn't have.

## 9. DNI client testing

- **Decision**: Playwright for the constitution-mandated browser-level tests of the insertion client, covering multi-page and SPA replacement, session stickiness across tabs, post-load DOM mutation (MutationObserver-driven replacement), consent grant/withdrawal, and default-number fallback.
- **Rationale**: These are exactly the scenarios the constitution calls out as unenforceable by server-side tests alone; Playwright drives real browser engines (not a DOM simulation), supports multi-tab scenarios (Edge Cases: "same visitor opens several concurrent tabs"), and integrates cleanly into the same CI pipeline as the xUnit suites.
- **Alternatives considered**: Cypress — comparable capability but weaker native multi-tab/multi-context support, which the concurrent-tabs edge case specifically needs; Playwright's built-in multi-context API is a better fit.

## 10. Retention and de-identification

- **Decision**: A scheduled Retention worker loop (§4) that, per data category, either hard-deletes (visitor/session identifiers at 14 months) or replaces identifying fields with a stable HMAC-derived, non-reversible surrogate (call/attribution/publication records, de-identified in place at the 14-month mark, retained a further 11 months to 25 total), skipping any row still referenced by an open manual review case (FR-040) or awaiting an erasure request's 30-day completion window (SC-019).
- **Rationale**: A stable surrogate (rather than deleting the linking key outright) is what FR-040 requires to keep historical reports and audit trails internally consistent after identifiers are gone — a keyed HMAC of the original identifier produces the same surrogate every time the same source value is re-encountered within a category, preserving joins without being reversible without the key.
- **Alternatives considered**: Hard delete with orphaned foreign keys — breaks FR-019's evidence-chain requirement and SC-014's "reports still reconcile" bar; rejected. Reversible encryption — technically satisfies "non-reversible" in spirit but not in fact, since the key's existence makes it recoverable; rejected as not meeting the letter of FR-040.

## 11. Rate limiting for the visitor-facing endpoints

- **Decision**: Fixed-window counters keyed on (origin, client token) held in-process per instance with periodic reconciliation, or a shared store (e.g., MySQL-backed counter table, reusing the existing database rather than adding Redis) if horizontal scale-out makes per-instance counting too permissive in practice; defaults of 600 req/min per origin and 10 req/min per client (FR-037).
- **Rationale**: At the platform's stated scale (~57 req/min system-wide peak, §Technical Context Scale/Scope), even a per-instance approximation comfortably enforces the FR-037 defaults without a new infrastructure dependency; a shared MySQL counter table is a low-effort upgrade path if the deployment later runs enough API instances for per-instance skew to matter.
- **Alternatives considered**: Redis-backed sliding-window rate limiting — the standard answer at larger scale, but an unjustified dependency addition against the stated ~630-number, ~250-concurrent-session sizing; noted as the first thing to revisit if Scale/Scope grows materially beyond what's stated in the spec.

## 12. Consent event/callback contract (FR-039)

- **Decision**: A single global JS contract published by the DNI client: `window.__attributionConsent = { granted: boolean }` readable synchronously on load, plus a `window.addEventListener('attribution:consent-change', handler)` custom event any CMP or custom consent tool dispatches on later changes. The DNI client reads the global on load and subscribes to the event for the life of the page view.
- **Rationale**: A single, versioned, minimal-surface contract is what makes FR-039's "any site's consent mechanism is wired to fire it, rather than a bespoke per-site adapter" true in practice — one thing for every deploying customer's consent tooling to call, documented once.
- **Alternatives considered**: A cookie/localStorage convention instead of a JS event — harder to subscribe to for real-time change notification (would require polling), which conflicts with FR-039's "acted on immediately" requirement; rejected.

## 13. Schema migrations

> **Superseded 2026-09-08** — with no .NET application left to own a migration runner, schema changes become plain, hand-authored, version-numbered `.sql` files applied directly against MySQL (e.g. via a simple ordered-filename convention and a `schema_migrations` tracking table, or whatever migration runner ships alongside Apiche if it offers one) rather than FluentMigrator. The underlying schema itself (`data-model.md`) and the up/down, reviewed-in-PRs discipline are unchanged — only the authoring language (SQL instead of C#) and the runner change.

- **Decision**: FluentMigrator, C#-authored, versioned migrations run as a startup/deploy step against MySQL.
- **Rationale**: With Dapper chosen over EF Core (§1), there's no ORM-provided migration tooling; FluentMigrator gives the same "migrations as code, reviewed in PRs" workflow the constitution's CI/CD gate expects, without pulling in a full ORM just for its migration runner.
- **Alternatives considered**: DbUp (plain SQL script runner) — simpler but loses the up/down, C#-testable migration authoring FluentMigrator offers; rejected as a minor ergonomics regression for no scale benefit. Flyway — mature but Java-centric tooling in an otherwise pure .NET deployment; rejected to avoid a second runtime dependency.

## 14. Qualification rule representation

- **Decision**: A qualification rule version is stored as a small structured condition set (direction, answered, minimum connected duration, website/campaign scope, time-of-day window) in relational columns/a constrained JSON document — not as arbitrary executable code — evaluated by one internal rule-evaluator function shared by every rule.
- **Rationale**: FR-023/FR-024 require rules to be configurable without code change and safely versioned; a constrained condition set keeps evaluation deterministic, unit-testable (Principle V) and auditable (every field of every version is inspectable), whereas an embedded scripting/expression language would reopen the "no fuzzy/heuristic logic" concern Principle I is guarding against in a different guise.
- **Alternatives considered**: A generic rule-expression DSL (e.g., stored JsonLogic/CEL expressions) — more flexible for future condition types, but unjustified against the five condition dimensions FR-023 actually names; deferred until a real requirement for open-ended conditions appears.

## 15. Multi-pool DNI matching (FR-050)

- **Decision**: A two-round-trip extension of the existing `POST /v1/dni/allocate` call, no new endpoint. First call (made on load, as today, regardless of consent state): for a website with `multi_pool_enabled`, the response always additionally carries `pools: [{pool_id, default_number}]` for every pool scoped to that website — safe to return pre-consent since it creates no session, allocates no number and stores no identifier (FR-039 is about those three actions, not about returning static pool metadata, the same class of data `Website.default_number` already exposes today). The client digit-normalized-matches (FR-009) each pool's `default_number` against the page, exactly as it already does for a single site-wide `default_number`. Once consent is granted and matching is done, the client issues a second `/v1/dni/allocate` call carrying the new optional request field `matched_pool_ids: string[]`; the server allocates one Tracking Number per requested pool and returns `session_id` plus `allocations: [{pool_id, number, expires_at}]` — one Session, many concurrent Allocations (data-model.md's `Allocation`). `POST /v1/dni/heartbeat` keeps the request shape `{session_id}` unchanged but its response becomes `allocations: [{pool_id, still_valid, number}]` for a session holding more than one. A website with `multi_pool_enabled = false` (the default) sees no shape change at all on either endpoint — `pools`, `matched_pool_ids` and `allocations` are simply absent, and the existing single-`number` response shapes are exactly what ships today.
- **Rationale**: Directly implements the five 2026-08-17 clarification decisions (spec.md) without inventing a new endpoint or changing any existing single-pool response shape, so FR-050's "websites with multi-pool matching disabled MUST continue to behave exactly as today" holds by construction rather than by extra branching logic. Splitting into two calls avoids the chicken-and-egg problem of needing the pool→number map before the client can know which pools are even present on the page, and avoids allocating (and starting the FR-018 attribution window for) a pool the page never actually displays. Batching every matched pool into one allocate call — rather than one call per matched pool — mirrors the same per-client rate-limit reasoning (FR-037) already applied to the heartbeat-batching decision: a real directory page can match many pools at once (the researched Mediahawk comparison returned ~80 pools for one site), and one-call-per-pool would multiply request volume with page complexity for no benefit.
- **Session lifetime across pages**: because different pages on the same multi-pool website may display different subsets of locations (unlike the single-pool case, where every page shows the same one number), a session's allocation set can grow over its lifetime — a later page view that matches a pool the session doesn't yet hold triggers an additional allocation for that pool under the same session, added to rather than replacing its existing allocations. This follows directly from FR-050's "every pool whose number is found... MUST be allocated from" applying continuously to each page view, not only to the first.
- **Cross-website pool validation** (2026-08-17 `/speckit-analyze` finding): `matched_pool_ids` is client-supplied on an unauthenticated, origin-restricted endpoint (FR-037), so it is untrusted input in the same way every other field on this endpoint already is. The allocation handler MUST filter it down to pools actually scoped to the request's own `website_id` before allocating from any of them, silently dropping the rest — the same treatment already given to any other out-of-scope or malformed part of a request on this endpoint, and the only way to keep one website's visitors from being able to exhaust a different website's pool.
- **Pool default-number uniqueness** (2026-08-17 `/speckit-analyze` finding): matching only works if a matched number identifies exactly one pool, so `Number Pool.default_number` MUST be validated unique among pools scoped to the same website whenever that website has `multi_pool_enabled` (data-model.md). This is an admin-time create/update check (`AdminPoolsController`, T037's endpoint), not a runtime one — by the time a visitor's browser is matching against the map, the map is already guaranteed collision-free.
- **Alternatives considered**: A single combined "match and allocate" call sent before consent is known — rejected, since it would need to either allocate speculatively pre-consent (violates FR-039) or defer the whole map fetch until after consent (which then delays even the pre-consent default-number display FR-008/FR-050 require to work per-pool from the start). Returning the full map as static site-owner-authored config (mirroring how `configuredNumbers`/`defaultNumber` already work today) instead of a live server fetch — rejected in favor of the clarified live-fetch approach, which needs no site-owner config work per pool and stays correct automatically as pools are added, removed or re-scoped administratively (FR-004).
- **Session-resume needs a `session_id` on `/allocate`** (2026-08-17 implementation finding): the client only calls `/allocate` at all when it has no session already cached (`sessionStore.js` — a full-page navigation with a live cached session skips straight to heartbeat, never re-calling `/allocate`). Multi-pool session growth (quickstart.md §2a step 7) requires the opposite on a later page view of a multi-pool site: the client must re-run local matching against that page and, if it finds a pool it doesn't yet hold, call `/allocate` again — but the server has no way to know which existing session to extend, rather than starting a new one, without being told. `dni-api.md`'s `/allocate` request therefore gains an optional `session_id`, sent only by a multi-pool client that already holds one; a single-pool client never sends it and keeps today's "skip `/allocate` once a session is cached" behavior byte-for-byte. Server-side, this reuses the existing atomic allocator's per-pool number-picking query unchanged, adding one sibling method (`TryAllocateAdditionalAsync`) that inserts an Allocation row against an already-persisted Session instead of creating a new Visitor and Session, used both for a fresh multi-pool session's second-and-later pool and for growing an existing one.

## 16. Server-side folder CSV import (FR-051)

- **Decision**: A configured local/mounted filesystem path (`NumberImport:FolderPath`) that an operator drops 8x8-exported CSVs into. Two new admin endpoints reuse the existing FR-002 row-validation logic exactly: `GET /v1/admin/numbers/import-folder/files` lists the CSV files currently in that folder (name, size, last-modified), and `POST /v1/admin/pools/{id}/numbers/import-from-folder` takes `{ file_name }`, resolves it strictly against `Path.GetFileName` (rejecting anything that isn't a bare file name directly inside the configured folder, so a crafted `../../` value cannot read outside it), and runs the identical per-row accept/reject logic the multipart-upload endpoint already uses, extracted into a shared helper so the two paths cannot silently drift apart.
- **Rationale**: The 8x8 admin portal has no API this platform can poll or integrate with directly; a human exporting a CSV and dropping it in a known location is the actual operational workflow, so the platform's job is to make triggering the already-specified FR-002 import from that location a first-class admin action rather than requiring a manual download-then-browser-upload round trip. Re-running the same accept/reject validation (rather than inventing folder-specific rules) means a file already partially imported is naturally safe to re-trigger: previously-accepted numbers reject as duplicates, and only genuinely new rows are added.
- **Alternatives considered**: Watching the folder and auto-importing on file arrival — rejected, since an administrator choosing which pool a given file's numbers belong to is a decision the system cannot infer from the file alone (the CSV format research.md §accepts is bare DIDs, one per line, with no pool column), so an explicit trigger naming both the file and the target pool is required regardless. Cloud object storage instead of a local/mounted folder — rejected per the 2026-08-17 clarification (spec.md), which fixed the drop location as a server-side folder for this version.

## 17. Architecture migration: replacing the ASP.NET Core/.NET backend with Apiche (2026-09-08)

- **Decision**: The hand-written ASP.NET Core Web API + Application/Domain/Infrastructure C# layers (§1–§9, §13 below) are retired and replaced by **Apiche**, a third-party, config-driven API gateway: every capability this platform exposes over HTTP becomes one versioned Apiche endpoint, each backed by exactly one parameterized SQL statement (`<parameter_name>` placeholders bound 1:1 to a GET/DELETE query-string parameter or a POST/PUT JSON body field). MySQL remains the database (unchanged, still 8.0+ for `FOR UPDATE SKIP LOCKED`). Background processing (8x8 CDR/Call Leg polling, Google Ads/GA4 publication, alert evaluation, retention/de-identification) moves from the bespoke `Attribution.Workers` `IHostedService` host to Apiche's own scheduled-job configuration, invoking the same SQL/stored-procedure layer described in §18. Full per-endpoint translation, including every stored procedure this requires, is enumerated in `apiche-config.md`.
- **Rationale**: This corrects a standing drift between the ratified constitution — Principle II and Principle VI have described Apiche and Basic-Auth-only access since the constitution's first ratified version — and this feature's actual Phase 0/1 design and implementation, which built a conventional layered .NET application instead. That drift was never surfaced as a Constitution Check violation because the check's own wording ("Layered Architecture... Presentation → Application → Domain → Infrastructure") was written to describe the .NET layering as if it satisfied Principle II, when Principle II's text is unambiguous that the backend **is** Apiche, not a framework that merely happens to be layered. This plan revision closes that gap rather than opening a new one.
- **What is retired**: `src/Attribution.Api` (controllers, middleware, DTOs), `src/Attribution.Application`, `src/Attribution.Domain`, `src/Attribution.Infrastructure` (Dapper repositories, FluentMigrator), and `src/Attribution.Workers` are all superseded as *runtime* components. Their C# source remains in the repository as the authoritative behavioral reference during migration — every stored procedure and Apiche endpoint in `apiche-config.md` is a direct translation of logic that already exists and is already unit-tested there — but no new feature work targets these projects going forward, and they are removed once the Apiche configuration and stored procedures reach parity (tracked as a migration task in the next `/speckit-tasks` run, not this plan).
- **What is unaffected**: `client/dni-script` (the DNI JavaScript client) and the externally-owned PHP/JS/CSS reporting portal are both API/DB consumers already, per Principle III and the constitution's client-boundary rules, and neither embeds business logic. The DNI client's request/response shapes (`contracts/dni-api.md`) and the reporting portal's direct read-only DB access are unchanged by this migration except for the Basic Auth addition covered in §20. MySQL's schema (`data-model.md`) is unchanged in shape; only the code path that reads and writes it changes.
- **Alternatives considered**: Keeping the .NET layers as a facade in front of Apiche (Apiche only fronting a subset of endpoints) — rejected, since the constitution requires Apiche to be the *entire* backend and "no other backend entry point"; a partial migration would leave two parallel, inconsistent authorization and audit models running at once. A full rewrite in a different framework that merely *emulates* Apiche's config-driven shape — rejected, since Apiche is a mandated third-party tool per the constitution, not a pattern to reimplement.

## 18. Business logic under Apiche's one-statement-per-endpoint constraint

- **Decision**: Every operation that the current C# Application/Domain layers implement as more than a single read or a single-row write — atomic number allocation (FR-003), idempotent CDR/Call Leg upsert (FR-017, FR-045), qualification-rule contiguity validation (FR-024), the zero-System-Administrator guard (FR-046/data-model.md's User constraint), conversion idempotency-key management (FR-027), audit-entry writes bundled with the state change they record (FR-035), and manual review resolution (FR-036, which must atomically supersede an Attribution row, write a Review Case resolution, and trigger any FR-044 correction) — is pushed down into a MySQL stored procedure. The corresponding Apiche endpoint's single SQL statement is then `CALL sp_<name>(<param1>, <param2>, ...)`. A plain single-table read or single-row insert/update with no branching (e.g. listing pools, reading integration health, an audit-log query) stays a direct parameterized `SELECT`/`INSERT`/`UPDATE` — there is no benefit to wrapping trivial statements in a procedure, and doing so everywhere would just relocate the SQL without adding safety.
- **Rationale**: This is the only way to satisfy Apiche's one-parameterized-statement-per-endpoint contract without weakening any of Principle I (deterministic matching, which depends on the same row-locked allocation-window logic already proven in §2), Principle IV (idempotent/auditable operations), or the FR-024/FR-046 validation rules that currently live in Domain-layer code. MySQL stored procedures support the same transactional semantics (`START TRANSACTION`/`COMMIT`, `SELECT ... FOR UPDATE SKIP LOCKED`, conditional `SIGNAL SQLSTATE` to reject an invalid request) the current C# code already relies on, so no business rule changes meaning — only where it is expressed changes.
- **Testing implication**: Principle V ("Test-First for Business Logic") now applies to stored procedures rather than to C# Domain/Application classes. Per the project's already-established testing convention (tests run against the shared remote MySQL database, not disposable containers — see the standing "tests run against shared remote DB" project preference), business-logic tests become a SQL-level test suite that calls each stored procedure directly (e.g. via a lightweight test runner using MySqlConnector or a `mysql` CLI harness) and asserts on result sets and resulting table state, seeded and torn down with randomized identifiers per test exactly as the existing integration tests already do. These tests must exist before or alongside each procedure, mirroring the xUnit-before-implementation discipline the constitution already mandates — only the test technology changes, not the requirement. The existing C# unit tests for allocation/attribution/qualification logic (`tests/Attribution.UnitTests`) become the reference oracle during migration: each stored procedure's test suite should assert the same input/output pairs those tests already assert, so behavioral parity is provable rather than assumed.
- **Alternatives considered**: Expressing complex logic as MySQL triggers instead of stored procedures — rejected, since a trigger fires implicitly on a plain `INSERT`/`UPDATE` rather than being invoked explicitly as a single named statement, making it harder for `apiche-config.md` to document "this is what this endpoint does" as one legible unit, and triggers compose poorly when one operation (e.g. manual review resolution) must touch several tables in a specific order with early-exit validation. Application-level business logic in a thin service Apiche calls out to per request — rejected, since that reintroduces exactly the "separate application logic" the constitution's worker-services language explicitly rules out, and would mean Apiche is no longer the entire backend.

## 19. Background/worker processing as Apiche scheduled jobs

- **Decision**: The four existing worker loops (Ingestion, Publication, Alerting, Retention) become Apiche scheduled-job configuration entries rather than a separate `Attribution.Workers` process. Each job entry has: a schedule (cron-equivalent cadence, e.g. hourly for CDR/Call Leg ingestion per FR-016), an external HTTP call description where one is needed (the 8x8 Analytics API poll; the Google Ads `ConversionUploadService` call; the GA4 Measurement Protocol POST), and a target SQL statement or stored-procedure call (per §18) that persists the job's results — the ingestion checkpoint advance and idempotent CDR/Call Leg upsert; the outbox-drain-and-publish bookkeeping; the alert raise/repeat/clear bookkeeping; the retention purge/de-identification sweep. `apiche-config.md`'s "Background Worker Jobs" section documents each job's schedule and SQL/procedure; the external-call side (endpoint URLs, auth, payload/response mapping for 8x8, Google Ads and GA4) is Apiche's job-connector configuration, whose exact configuration surface is vendor-specific and therefore out of this document's scope — it is bound to Apiche's actual connector schema at implementation time, exactly as any third-party tool's non-SQL configuration would be.
- **Rationale**: The constitution states this directly ("Apiche also owns all background/worker processing... these run as Apiche worker services, not separate application logic"), so this is not a novel design choice so much as applying the same "one config-driven job, no bespoke code" philosophy already established for inbound HTTP endpoints to outbound/scheduled work. The prior `Attribution.Workers` rationale (§4 below) — isolating ingestion/publication failure modes from the visitor-facing allocation path (FR-043) — still holds and is satisfied by Apiche's job scheduler running independently of Apiche's HTTP-serving path, the same isolation property a separate host previously provided.
- **Open item carried to implementation**: because Apiche's specific mechanism for an outbound HTTP call within a scheduled job (retry/backoff policy, credential storage for 8x8/Google Ads/GA4, response-to-SQL-parameter mapping) is not specified in the brief this plan was given, and no public Apiche product documentation is available to this planning process, the exact job-connector syntax is a **documented assumption, not a resolved unknown**: assume Apiche supports a job type that performs one outbound HTTP call per scheduled tick and maps named fields of the response into the placeholders of one associated SQL statement/stored-procedure call, mirroring how Apiche already maps URL/body fields to placeholders for inbound endpoints. If Apiche's real connector model differs materially (e.g. it requires an intermediate transform function, or cannot itself make outbound HTTP calls at all), `apiche-config.md`'s worker-job section will need re-authoring against Apiche's actual documentation before implementation — this is flagged explicitly in that document's Coverage Notes rather than silently assumed away.

## 20. Authentication and authorization under Apiche (Basic Auth only — supersedes §5, FR-046 and SC-016)

- **Decision**: All three constitution-defined credential shapes are Basic Auth, verified fresh on every request (no sessions, no bearer tokens, no MFA challenge at the API layer):
  1. **DNI JavaScript client**: a per-website Client ID/secret pair, sent as the Basic Auth username/password on every `/v1/dni/*` call. This is checked against a `website_credentials` table (or Apiche's native credential store, if it offers one, configured per website) and carries no role. Origin restriction and rate limiting (FR-037) remain as defense-in-depth layered on top of this credential, unchanged.
  2. **Interactive human users** (System Administrator, Marketing Administrator, Analyst): a per-user long-lived Basic Auth username/password, checked against a `users` table on every request, with the row's `role` column enforced as authorization. There is no login endpoint, no session, and no token: revocation is simply setting `is_active = false` on the row, which takes effect on the very next request — strictly stronger than FR-046/SC-016's "within one 5-minute refresh interval" bound, since there is no interval to wait out at all.
  3. **System-to-system integrations** (Integration Service role): an API key used as the Basic Auth password against a fixed identifying username, checked the same way as a human user's credential but against a row with `identity_type = integration_service`, which is barred from any endpoint flagged as interactive-only (FR-038's existing rule, unchanged).
- **What this explicitly supersedes**: FR-046's local username/password **+ mandatory TOTP** requirement, and its short-lived JWT access token / rotating refresh token pair, are dropped in full — Basic Auth has no per-request MFA challenge mechanism and no session to attach a refresh cycle to. SC-016's specific verification mechanism ("their next refresh attempt is refused and their already-issued access token is rejected once it expires") no longer applies as written, since there is no refresh attempt or access token; SC-016's underlying *property* (a deactivated account loses access without a separate revocation action) is preserved, and strengthened to immediate effect. This was raised to the project owner during this planning session and confirmed: Basic Auth is the deliberate, accepted trade-off, chosen over preserving TOTP by building a non-Apiche authentication shim in front of it — see the rejected alternative below. **`spec.md`'s FR-046 and SC-016 were formally amended to reflect this decision in the 2026-09-08 `/speckit.clarify` session** (spec.md's Clarifications, "Session 2026-09-08"), which post-dated this research decision and confirmed it.
- **Password storage**: unchanged in spirit from FR-046's original text — a user's Basic Auth password is stored only as a salted hash (e.g. bcrypt/argon2), verified by a stored procedure that never returns the hash itself, never logged, and never placed in an Apiche config file in plaintext, consistent with the constitution's "secrets never stored in source control or logs" rule. An Apiche endpoint credential (the DNI client ID/secret, the Integration Service API key) is likewise never embedded in `apiche-config.md` or any versioned file — the config document enumerates *placeholder names* and *SQL*, never actual secret values.
- **Every sign-in/auth check audited**: FR-046's "every sign-in attempt, successful or failed, MUST be audited" is preserved, reinterpreted as "every failed Basic Auth check against a human or integration credential is written to the audit log" — since there is no discrete sign-in event anymore, the audit boundary moves from "login" to "authentication failure on any request," which is at least as strong a signal.
- **Alternatives considered**: A thin non-Apiche authentication microservice that issues JWTs after a local username/password + TOTP check, sitting in front of Apiche only for the human-facing surface — this was offered to the project owner as an option and explicitly declined in favor of the simpler, fully-Apiche-native Basic Auth model, on the reasoning that it would make Apiche the entire backend in name only (an un-mandated bespoke service would still exist, and "no other backend entry point" would no longer be true). Keeping TOTP as a client-side second factor bundled into the Basic Auth password field (e.g. `password:totp_code` concatenated) — rejected as security theater: TOTP codes expire every 30 seconds, so a static Basic Auth credential cannot legitimately embed one without either being rejected almost immediately or requiring the credential to be re-entered constantly, defeating the point of a long-lived credential.

## 21. `apiche-config.md` as a generated migration artifact

- **Decision**: `apiche-config.md` (sibling to this file) enumerates, endpoint by endpoint, every HTTP surface the current .NET implementation exposes — translated per §18–§20 into Apiche's method/path/parameters/single-SQL-statement shape, with every required stored procedure's full body in an appendix, and the four background jobs from §19 in their own section.
- **Rationale**: This is the concrete, checkable deliverable that proves the migration is complete and behaviorally equivalent — a reviewer can diff it against the existing `contracts/*.md` files and the current controllers to confirm nothing was dropped, and it becomes the literal Apiche configuration input once implementation begins.
- **Relationship to `contracts/*.md`**: the existing contract files remain the authoritative source for *request/response shape and business rules* (what each endpoint must do and why); `apiche-config.md` is the authoritative source for *how Apiche is configured to do it* (method, path, parameter-to-placeholder mapping, SQL). Where the two might drift, `contracts/*.md` wins for behavior and `apiche-config.md` should be regenerated to match, not the reverse.
